# План реализации мокапа «RENVI для всех»

Документ для следующего исполнителя: по нему можно продолжать без истории чата. Обновляйте отметки в каждом PR.

## Как устроена работа

- Одна задача — одна ветка и один небольшой PR. PR самостоятельно не объединять: объединяет владелец.
- Стек прежний: Expo / React Native / TypeScript / Expo Router (`src/app`), Supabase. Мокап — образец, экраны нативные.
- Проверки перед PR: `node scripts/check-i18n.mjs`, `check-client.mjs`, `check-release.mjs`, `node --test scripts/tests/*.test.mjs`; в CI дополнительно tsc, lint, сборка веба, база и сквозные тесты (`e2e/run-all.sh`).
- Все тексты — через `src/i18n` на пяти языках (ru, sk, cs, en, ua); `check-i18n` сверяет ключи и `{подстановки}`.
- Изменения базы — только новыми миграциями (последняя на момент записи — 0034).
- Исходный HTML мокапа в репозиторий не кладём. Нужные числа и тексты записаны в тестах и в этом файле.
- Честно указывайте, что проверялось: локально нет ни `npm`, ни `tsc`, ни iOS, поэтому интерфейс проверяется в CI (веб, 393×852), а на iPhone — владельцем.

## Что нужно знать о самом мокапе

- В файле два слоя экранов. Сначала идут старые определения (`case'welcome'` и т. д. в первой половине скрипта), ниже — новые («RENVI для всех»), которые перекрывают старые. **Побеждает последнее определение.** Читать нужно вторые `case'…'` в конце файла.
- Файл на 4 МБ почти целиком состоит из картинок base64; читать его удобно, предварительно вырезав `data:image/...;base64,...`.
- Самый надёжный способ узнать размеры — открыть файл в Chromium с окном 393×852 и измерить элементы (`getComputedStyle`, `getBoundingClientRect`). Ширина до 820 px включает мобильные правила: например, заголовок обложки на телефоне 44 px, а не 43.
- Токены (цвета, радиусы) уже совпадают с мокапом: `src/theme/tokens.ts`. Общие компоненты: `src/components/ui.tsx` (Btn, Choice, Field, Title, BackLink, LinkBtn, Chip, Card, Sheet…), `Tag` и `Mosaic`/`Tile` (задача 1), иконки `UiIcon`.

## Решения, которые должен принять владелец

Мокап противоречит текущим правилам продукта в этих местах. Они не приняты молча, независимые задачи идут дальше.

1. **Деньги — решено 2026-11-06: возвращаем (Plus, подъём, реклама, Playbook).** Было: в мокапе есть тарифы Free и Plus, подписка «RENVI Plus», реклама в ленте, реклама за награду, платный «Подъём плана» 0,99 €, лимит планов в Free, платные гайды. Сейчас приложение бесплатное, подписки и покупки убраны (миграция 0029, решение владельца). Нужно решить: возвращать ли оплату, какие тарифы и что считать платным; для App Store это ещё покупки внутри приложения и их ревью.
2. **Языки.** Мокап показывает 4 языка (SK, CS, RU, UA), приложение поддерживает 5 вместе с английским, и все пять полностью переведены. В задаче 1 английский сохранён. Скажите, убирать ли его.
3. **Статус отношений и общий профиль пары.** «В отношениях», «В браке», «Мы пара — общий профиль», связка пары по коду: это чувствительные данные по GDPR. Нужны согласие, правила видимости и серверная проверка.
4. **Смена продукта.** Мокап превращает приложение из сервиса знакомств в приложение для компаний, планов, друзей, пар и свиданий. Это затрагивает описание в App Store, возрастной рейтинг, App Privacy, политику, условия и правила сообщества (публичные встречи, безопасность), модерацию и аналитику. Тексты в `docs/site` и `docs/STORE_LISTING.md` придётся обновить.
5. **Обложка обещает то, чего ещё нет.** Плитки «Глинтвейн на рынке — 5 из 10 идут», «Падел 2×2», «Пары», «Компания по интересам» показывают планы, компанию и пары, а подписи в них примерные. Пока задачи P и S не сделаны, нельзя отправлять сборку в магазин с этой обложкой: Apple может счесть описание вводящим в заблуждение. Плитки и их тексты вынесены в `TILE_STYLE` и в ключи `screens.index.tile*`, их легко заменить.
6. **Обращение.** Новые экраны мокапа говорят «ты», старые (вход) — «вы». В приложении оставлено как в мокапе; единый стиль стоит выбрать.
7. **Гайды.** В приложении уже есть `playbook/*` (обучающие материалы). Мокап называет их «Гайды» и делает частично платными; сверить в задаче M.

## Журнал планов, часть 2 (миграция 0041)

- **«Всё ок?» в 21:00.** Функция `plan-check` (по расписанию, тот же секрет `DIGEST_CRON_SECRET`, что у `weekly-digest`) шлёт пуш хосту и принятым участникам в 21:00 по местному времени дня плана (SK/CZ — Братислава/Прага, UA — Киев; если план начался поздно — через 2 часа после начала; окно отправки 6 часов). Пуш без названия, места и имён, открывает «Как прошло». База сама решает, кто должен получить, и «занимает» пару (план, человек) до отправки: повторно не уйдёт. Выключатель — «Уведомления → Вечером после плана». На экране «Как прошло» два ответа: «Всё хорошо» / «Нужна помощь» (второй открывает «Безопасность»); ответ видит только сам человек, другим участникам он не показывается.
- **Опросы в чате плана.** Любой участник создаёт опрос (вопрос + 2–6 вариантов), максимум три открытых на план. Голос можно менять до закрытия; закрыть может автор или хост. Видны только цифры, кто как голосовал — нет. Счётчики обновляются раз в 10 секунд и при новом сообщении.
- **«В компанию» после плана.** Кнопка у каждого, кто пришёл (хост или отметившийся на месте). Это обычный «Привет» из «Компании»: чат откроется только при взаимном, блокировки и закрытый режим «Компания» учитываются на сервере.
- Тесты: `supabase/tests/plan_extras.sql` (40 проверок), `plan_check_text.test.ts`; e2e `modes-plans` (опрос, ответ на «Всё ок?», «В компанию»).
- Проверено только в вебе и в БД-тестах. **Не проверено на iOS:** сам приход пуша и открытие экрана по нажатию (нужен TestFlight-билд и расписание на проде).
- Решение владельца: пуш «Всё ок?» работает только при настроенном расписании (см. `docs/SETUP.md`, раздел «Вечерняя проверка планов»).

## Журнал: фиксированный search_path (search-path)

- Миграция `0044_fixed_search_path.sql`: `ALTER FUNCTION … SET search_path = public` для семи функций из аудита (`touch_updated_at`, `guard_profile_update/insert/delete`, `guard_photo_update`, `profiles_set_published_at`, `profile_details_json`). Тела, владельцы, триггеры и права не менялись; старые миграции не правились.
- Проверка зависимостей: тела обращаются только к объектам с явной схемой (`public.is_admin()`) или из `pg_catalog`; ни одна функция не `SECURITY DEFINER`, поведение не меняется.
- Тест `supabase/tests/search_path.sql` (9 проверок): у всех семи есть `search_path`, ни у одной `SECURITY DEFINER` функции в `public` его не нет, защитные триггеры работают как прежде.
- `referral_lookup` (единственная функция, доступная анониму): возвращает только имя пригласившего по коду; сознательный публичный контракт для страницы приглашения. Ограничения частоты на уровне БД нет — защита опирается на длину случайного кода и лимиты API Supabase; при желании можно добавить лимит отдельным решением.
## Журнал: входящий RevenueCat webhook (rc-webhook)

- Миграция `0043_revenuecat_events.sql`: журнал обработанных событий и «курсор» последнего события на человека; `rc_event_claim` / `rc_event_done` / `rc_event_release` только для service_role.
- Функция `revenuecat-webhook`: авторизация по `REVENUECAT_WEBHOOK_SECRET` (без секрета — 401), событие лишь сигнал, состояние берётся из RevenueCat и пишется `plus_set`. Продление, истечение, возврат (приходит как `CANCELLATION`), отмена отмены, перенос между пользователями (`TRANSFER`) — через один путь. Бусты не трогает (их применяет `boost-sync`). Реферальный Plus не затрагивается.
- Тесты: `supabase/tests/revenuecat_events.sql` (18 проверок, в т.ч. «промо переживает возврат»), `revenuecat_webhook.test.ts` (8).
- Проверено локально (БД-тесты, логика под Node). **Не проверено:** реальные события RevenueCat и sandbox-покупка на iPhone — нужны ключи; ответ «Send test event» из панели RevenueCat после деплоя.
- Старая функция в проде не менялась.
