# RENVI: подтверждение почты и восстановление доступа

Клиент всегда отправляет новую регистрацию на экран подтверждения. Серверная миграция `0026_identity_auth.sql` проверяет `auth.users.email_confirmed_at` перед публикацией и основными действиями приложения. Это не заменяет настройку Supabase Auth: если подтверждение выключено, Auth автоматически выставляет дату подтверждения, и сервер не сможет отличить такой аккаунт от подтверждённого по письму.

## Hosted Supabase — обязательные ручные настройки

1. В Authentication → Providers → Email включите **Confirm email** (`enable_confirmations = true`). Не выключайте для устранения проблем с доставкой.
2. В Authentication → URL Configuration укажите действительный HTTPS Site URL. В Redirect URLs добавьте точные адреса: `renvi://auth-callback`, `renvi://reset-password`, `https://ВАШ_ДОМЕН/auth-callback`, `https://ВАШ_ДОМЕН/reset-password`. Для GitHub Pages с `EXPO_PUBLIC_BASE_PATH=/renvi` нужны `https://ВАШ_ДОМЕН/renvi/auth-callback` и `https://ВАШ_ДОМЕН/renvi/reset-password`.
3. Настройте свой SMTP в Authentication → SMTP: провайдер, сервер, порт, учётные данные, отправитель RENVI. Проверьте подтверждённый домен отправителя, SPF/DKIM/DMARC, доставку и ограничения отправки. Встроенная доставка Supabase не является готовой доставкой писем реальным пользователям.
4. В Email Templates перенесите `supabase/templates/confirmation.html` (Confirm signup, тема «Подтвердите почту в RENVI») и `supabase/templates/recovery.html` (Reset password, тема «Восстановление доступа к RENVI»). Ссылки используют `.RedirectTo`, `.TokenHash` и явный тип, поэтому работают на новом устройстве без локального PKCE verifier. Время жизни токена задаётся в Auth; не добавляйте трекеры, аналитику или переписывание ссылок почтовым провайдером.
5. Проверьте регистрацию, повторное письмо, уже использованную и истёкшую ссылку, открытие на другом устройстве и восстановление пароля. При открытии на компьютере ссылки `renvi://` требуют установленное приложение: веб-регистрации используют HTTPS callback.

Никакие hosted-настройки, SMTP или шаблоны не применяются автоматически коммитом. Секреты SMTP задаются только в Supabase/secret storage. Развёртывание миграции также выполняется отдельно авторизованным оператором.

## Локальная среда и CI

`supabase/config.toml` включает подтверждение и локальные шаблоны. Supabase start предоставляет Mailpit (или Inbucket в старых CLI), обычно `http://127.0.0.1:54324`; используйте фактический `INBUCKET_URL` из `supabase status -o env`. Настройте callback URL локального веб-приложения в allowlist. Изменения Auth config требуют перезапуска локального Supabase.

`e2e/signup.e2e.mjs` создаёт обычный неподтверждённый аккаунт, проверяет блокировку входа, читает настоящее локальное письмо, открывает ссылку в новом контексте браузера, входит и проходит onboarding. `e2e/auth.e2e.mjs` проверяет повторное письмо, неверную/использованную ссылку и восстановление пароля через настоящее письмо. `e2e/mail.mjs` поддерживает API Mailpit и Inbucket. Тесты требуют локального почтового сервиса; они не подменяют email confirmation административным API. Служебные заранее подтверждённые аккаунты допустимы только для остальных E2E fixtures.

Полные письма, URL с токенами и browser storage state нельзя публиковать в CI artifacts. Снимки callback должны делаться после удаления credentials из адресной строки. Нативные `renvi://` переходы требуют установленной development/release сборки со scheme из app config; Expo Go не подтверждает поведение production scheme.

## Дата рождения и гендер

Первое ненулевое значение фиксируется серверным триггером, включая существующие значения при миграции. Прямые UPDATE/UPSERT и onboarding RPC не обходят блокировку. Точная дата хранится в `private_profile`; owner-only `my_identity()` возвращает её владельцу. Возраст в публичных RPC вычисляется на текущую дату UTC при чтении. Для 29 февраля день рождения в невисокосный год наступает 1 марта.

Администратор исправляет оба значения через `admin_correct_identity(uuid,date,text,text)` с обязательной причиной. Изменение и значения до/после записываются в защищённый `admin_actions`. Изменение напрямую даже администратором не открывает общее редактирование identity. Поддержка должна проверять обращение перед исправлением; пользовательские экраны ссылаются на поддержку.
