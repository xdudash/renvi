### Блокер платежей: старый revenuecat-webhook

Развёрнутый index.ts читает поля:
`user_id, tier, store, sandbox, expires_at, product_id, last_event_ms`,
обращается к `billing_events` и вызывает `billing_commit`.

В проде сейчас отсутствуют и `subscriptions`, и `billing_events`; RPC `billing_commit` также отсутствует.
Новая 0039 создаёт подписку с полями `user_id, product, trial, expires_at, store_checked_at, updated_at`.
Старый обработчик не соответствует этой модели. В его Dashboard на момент проверки отображалось 0 вызовов после деплоя; custom secrets отсутствуют.

Новые `plus-sync` и `boost-sync` — пользовательские POST-endpoint'ы: они проверяют JWT вызывающего пользователя, сами запрашивают RevenueCat и затем вызывают RPC.
Это **не готовый входящий обработчик RevenueCat webhook**.

Задача исполнителю:
- реализовать/проверить обработчик событий RevenueCat для новой модели, включая повторы, устаревшие события, истечение и возвраты; либо явно зафиксировать согласованную модель синхронизации без webhook;
- не направлять RevenueCat webhook на plus-sync/boost-sync;
- не включать старый endpoint как способ «быстро подключить» платежи;
- после замены отдельно вывести старую функцию из эксплуатации, не удалять её вслепую в рамках deploy-all.

Без платежных ключей можно проверять остальные функции приложения; это не подтверждает готовность монетизации.

### Пробел push для чатов планов

В проверенном `supabase/functions/push/index.ts` обрабатываются только:
- messages INSERT;
- matches INSERT;
- dates INSERT/UPDATE;
- video_calls INSERT/UPDATE.

Ветви `plan_messages` нет. `plan-check` отвечает только за вечернюю проверку и открытие `/plan-after`; это не доставка сообщений группового чата.

До проверки push по чату плана на iOS нужны:
- обработчик plan_messages с маршрутом в соответствующий план-чат;
- получение только разрешённых получателей с учётом участия/блокировок/настроек уведомлений;
- серверный webhook на новое событие;
- тесты выбора получателей, отсутствия имён/текстов сообщения в push, повторов и перехода на устройстве.

Наличие пуша «искра» также нельзя выводить из текущего обработчика: ветви sparks в нём нет. Если такой пуш входит в согласованный релиз, проверить его реализацию отдельно.

### Секреты

Не вставлять значения в Git, PR, отчёты, скриншоты или чат. Использовать защищённый ввод/менеджер секретов.

| Где | Имя | Назначение |
|---|---|---|
| Edge Functions | PUSH_WEBHOOK_SECRET | Авторизация Database Webhooks функции push |
| Edge Functions | DIGEST_CRON_SECRET | Авторизация weekly-digest и plan-check |
| Edge Functions | REVENUECAT_SECRET_KEY | Запросы к RevenueCat; требуется для платежей |
| Edge Functions | PLUS_ENTITLEMENT | Необязательно, по умолчанию plus |
| Edge Functions | RESEND_API_KEY + адреса отправителя | Необязательно для писем функций; SMTP Auth настраивается отдельно |
| Edge Functions | DAILY_API_KEY | Необязательно, только видеозвонки |
| Vault | project_url | URL проекта |
| Vault | digest_cron_secret | То же значение, что DIGEST_CRON_SECRET |
| EAS | EXPO_PUBLIC_REVENUECAT_IOS_KEY | Публичный SDK key приложения iOS, не secret key |
| GitHub production/repository secrets | SUPABASE_ACCESS_TOKEN, SUPABASE_DB_PASSWORD, SUPABASE_PROJECT_REF | Доступ workflow деплоя; наличие не проверено этим аудитом |

Секрет входящего RevenueCat webhook определяется реализацией нового обработчика; в проверенном main такого обработчика нет.

### Расписания и события

Сначала применить миграции и развернуть подходящие функции; затем настроить секреты и только потом активировать вызовы.

- pg_net нужен для net.http_post; сейчас отсутствует.
- plan-check: `*/15 * * * *`, заголовок x-digest-secret из Vault.
- weekly-digest: `5 * * * *`; функция ограничивает отправку настройкой и журналом.
- Сохранить существующий renvi-analytics-retention, не создавать дубликаты.
- Настроить вебхуки для таблиц, которые реально поддерживает push; plan_messages — после доработки обработчика.
- Проверить совпадение ключа функции и соответствующего значения Vault без вывода значений.
- При тестах не отправлять массовые push/письма реальным пользователям.

`supabase/config.toml` уже задаёт verify_jwt=false для push/weekly-digest/plan-check; их защищает собственный секрет.
Пользовательские delete-account/export-data/playbook-sync/plus-sync/boost-sync используют JWT.
Не снимать JWT-защиту со всех функций одним общим флагом.

## Auth: что подтверждено

- Email provider включён; подтверждение почты включено.
- Новая регистрация разрешена; anonymous sign-in выключен.
- Custom SMTP включён: Hostinger, smtp.hostinger.com:465. Пароль не читался и не менялся.
- Это проверка конфигурации, а не успешной доставки письма.
- Allow list содержит renvi://**, exp://**, Pages auth-callback и reset-password.
- Site URL остаётся старым Netlify-адресом. Для iOS с явным разрешённым redirect это не автоматически ошибка; перед публичным релизом согласовать канонический URL и проверить шаблоны/переходы.
- End-to-end на устройстве: подтверждение, сброс пароля, приглашение, ссылка плана.

Не менять Site URL и не отключать подтверждение почты для обхода ошибок.

## Предупреждения безопасности

В SQL подтверждены семь public-функций без фиксированного search_path:

- guard_photo_update
- guard_profile_delete
- guard_profile_insert
- guard_profile_update
- profile_details_json
- profiles_set_published_at
- touch_updated_at

Нужна отдельная новая миграция после согласования номера с текущим исполнителем.
Сначала проверить определения и используемые схемы, затем задать корректный search_path и прогнать регрессионные тесты.
Не править применённые миграции 0001–0035 задним числом.

Единственный public SECURITY DEFINER, исполняемый anon по SQL-проверке: referral_lookup.
Проверить намеренный публичный контракт приглашения, объём возвращаемых данных и защиту от перебора.

Остальные показанные предупреждения включают исполнение SECURITY DEFINER авторизованными пользователями.
Это не означает, что все такие функции уязвимы: для админских/пользовательских RPC проверить auth.uid(), принадлежность, is_admin() и лимиты.
Массовый REVOKE или замена на SECURITY INVOKER без анализа сломают предусмотренный доступ.
