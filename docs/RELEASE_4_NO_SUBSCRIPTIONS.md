# RENVI без подписок (release 4)

**Решение основателя (2026-10-29):** RENVI выходит бесплатным. Нет Plus/Premium, покупок в приложении, RevenueCat,
пейволлов, предложений «перейти на тариф» и значков тарифа. Миграция: `supabase/migrations/0029_remove_subscriptions.sql`.

## Как приложение работает теперь

| Функция | Было | Стало |
|---|---|---|
| Входящие искры | Free видел только число, список — Plus/Premium | Каждый видит, кто отправил искру: имя, возраст, город, комментарий (`incoming_sparks`, до 100 строк; правила видимости, блокировок, пропусков и матчей прежние) |
| Отмена последнего пропуска | Plus/Premium (`plan required`) | Для всех (`undo_last_pass`), кнопка «↶ Отменить последний пропуск» всегда видна |
| Режим инкогнито | Premium | Для всех (`save_onboarding`, прямой `UPDATE` своей анкеты); правило видимости из 0020 не менялось |
| Фильтр «только фото-проверенные» | Plus/Premium | Для всех (`save_filters`, прямой `UPDATE`) |
| Лимит искр | Free 20 / Plus 100 / Premium 300 в день (`tier_limits`) | Один анти-спам лимит для всех: `app_config.daily_spark_limit`, по умолчанию **100** за сутки UTC |
| Экран лимита | «Лайки закончились» + «Посмотреть RENVI Plus» | Нейтрально: «Лимит на сегодня исчерпан» / «Возвращайтесь завтра…», кнопка «Вернуться к знакомствам» |
| Приглашения | Награда днями Plus после решения админа | Приглашения, ссылка, прогресс «N из цели» и проверка админом остаются; одобрение только засчитывает приглашение (статус `rewarded` в базе = «засчитано»), никаких наград |
| Уведомление «Новые симпатии» | Включалось только при доступе к входящим | Доступно всем |

Лимит держит сервер: `send_spark` считает искры пользователя с начала текущих суток UTC и при достижении
`daily_spark_limit()` отвечает `daily limit` (SQLSTATE `P0003`, без слов о тарифах). Неверное или отсутствующее значение в
`app_config` даёт 100, а не «без лимита». Клиент заранее показывает экран лимита по `likes_today` и тому же значению
(`useSparkLimit`), но решает сервер. Админ меняет число в «Настройки» → «Дневной лимит искр» (1–100000, `admin_config_set`
проверяет и пишет в журнал).

## Развёртывание

1. Слить PR. Веб публикуется автоматически; сразу после этого запустить **Deploy Supabase** (применит 0029). До применения 0029 новый клиент на старой базе: список входящих пуст для бывших Free, отмена пропуска уводит на экран ошибки — окно нужно держать коротким.
2. Если в базе уже есть реальные покупки и их историю нужно сохранить — **до** миграции выгрузить:
   `pg_dump "$DATABASE_URL" -t public.subscriptions -t public.billing_events -f billing-backup.sql`. 0029 удаляет эти таблицы без возможности восстановления.
3. Удалить развёрнутую функцию и секрет: `npx supabase functions delete revenuecat-webhook`, `npx supabase secrets unset REVENUECAT_WEBHOOK_SECRET`. Удалить вебхук в RevenueCat и сам проект RevenueCat (или отключить).
4. GitHub → Settings → Variables: удалить `EXPO_PUBLIC_REVENUECAT_IOS_KEY`, `EXPO_PUBLIC_REVENUECAT_ANDROID_KEY`.
5. App Store Connect / Google Play: снять подписки Plus/Premium с продажи; если есть действующие подписчики — отменить и вернуть деньги через магазины (сервер больше ничего о них не знает). В описании приложения и скриншотах убрать упоминания платных функций.
6. Новые нативные сборки (`eas build`): из бинарника уходит нативный модуль RevenueCat (и Android-разрешение `BILLING`). Для уже установленных сборок можно выпустить `eas update` — JS-бандл без RevenueCat работает на старом бинарнике (модуль просто не используется). Старые бандлы без обновления читают таблицу `subscriptions`, которой больше нет: сессия отмечает ошибку загрузки и показывает её, пока приложение не обновится.

## Риски и что не проверено

- Удаление таблиц необратимо (см. шаг 2). На хостинге миграция не запускалась; проверено на локальном Postgres 16 со стабом `auth`.
- Анти-спам лимит 100/сутки — значение по умолчанию из задачи; его стоит пересмотреть по реальной активности (меняется без сборки).
- Счёт идёт по суткам UTC (`date_trunc('day', now())`), как и раньше; повторная искра после конца матча тоже считается искрой.
- Сервер по-прежнему принимает экранный id `subscription` в `analytics_record` (старые сборки, исторические строки); новый клиент его не отправляет.
- Статус приглашения в базе остался `rewarded` (ограничение `check`), в интерфейсе он означает «засчитано».
- Нативный iOS/Android-бинарник и EAS-сборка без `react-native-purchases` не собирались в этой среде (npm-реестр недоступен); `package-lock.json` изменён `npm uninstall --package-lock-only --offline` и проверен на целостность.
- Полный `tsc` и ESLint не запускались (нет `node_modules`); каждый изменённый файл проверен `ts.transpileModule` и частичной семантической проверкой на неиспользуемые импорты/неизвестные имена.
